# Releasing a story as a desktop application

The desktop channel wraps the same folder the web channel publishes in a native
window: a Windows installer, a Linux `.deb`/AppImage, a macOS `.dmg`. The reader
double-clicks an icon rather than a file, and no browser is involved.

It consumes a bundle, not a `.vnerelease`. That is deliberate — one reader of
the container, one answer to "what is in this release", and no way for the
desktop copy and the web copy to drift into being different novels.

```bash
pnpm export:story --release novel.vnerelease --out ./novel-web
pnpm build:desktop --bundle ./novel-web --out ./novel-desktop
```

## What you need

Two things this repository cannot install for you:

| | |
| --- | --- |
| **Rust** | <https://rustup.rs>. Reopen the terminal afterwards. |
| **Tauri CLI** | `pnpm add -D @tauri-apps/cli@^2` |

and one per platform:

- **Windows** — the MSVC build tools (Visual Studio Build Tools with "Desktop
  development with C++"). WebView2 is already on Windows 10 and 11.
- **Linux** — `libwebkit2gtk-4.1-dev`, `build-essential`, `libssl-dev`,
  `libayatana-appindicator3-dev`, `librsvg2-dev`, `patchelf`.
- **macOS** — Xcode command line tools.

The Tauri CLI is not a dependency of this project on purpose: it ships a
prebuilt binary per platform and is useless without a Rust toolchain, which no
lockfile can install anyway. Everyone who is not building a desktop app carries
neither.

`pnpm build:desktop --stage-only` needs none of it. It writes the project and
stops, which is how the pipeline is tested on machines with no Rust at all.

## What gets built

```
novel-desktop/
  frontend/          the exported bundle, verbatim
  src-tauri/
    tauri.conf.json  productName, version and identifier, filled from the release
    Cargo.toml
    src/main.rs
    capabilities/
    icons/           generated by `tauri icon`
```

Then `tauri build`, and the installer lands under
`src-tauri/target/release/bundle/`.

## The identifier, and why it decides whether saves survive

Every desktop application has an identifier. On Windows it decides which WebView2
data directory the app gets — and that directory is where the reader's saved
games live. It is derived from the **story id** and nothing else:

```
com.vne.story.<readable part of the story id>.s<hash of the whole story id>
```

So renaming the novel, changing the author, or bumping the version leaves it
alone, and v2 installs over v1 with every save intact. Two different stories can
never land on the same identifier even when their readable parts collapse to the
same text, because the trailing segment hashes the whole id — otherwise one
novel's installer would replace another's and inherit its saves.

The rules live in [`lib/release/native-identity.ts`](../lib/release/native-identity.ts)
and are shared with the Android channel, which has the same problem under a
different name.

## Names and versions the platform will accept

- **The product name** is the story title with everything a Windows filename
  cannot hold removed. Novel titles carry colons and question marks far more
  often than software names do, and an unsanitized one fails deep inside the
  installer bundler with an error naming neither the title nor the character.
- **The version** is the release version, unchanged. Windows Installer records it
  as three fixed-width fields, so `256.0.0` or `1.0.70000` is refused rather than
  clamped: clamping would make two different releases install as the same
  version, and an installer that believes it is already up to date is worse than
  one that never ran.

## The icon

`tauri icon` generates the whole set from one square PNG of at least 512px.
The story cover is used when it is one — most covers are portrait, so most
stories fall back to the engine icon, and the script says which happened and
why. Pass `--icon <file.png>` to choose.

## What the application is allowed to do

Nothing. The window registers no commands, so the page has no IPC to call, and
the capability grants `core:default` and nothing else — no filesystem, no shell,
no HTTP client. A novel is data a stranger runs; the shell must not become a way
for one to reach the machine it plays on. Both files are checked by a test, not
by review.

The page keeps its own Content-Security-Policy rather than letting Tauri inject
one: the same folder has to play double-clicked from a filesystem, where
`default-src 'self'` is unsatisfiable.

## Unsigned, and what a reader sees

Installers built without a code-signing certificate are unsigned, and every
desktop platform says so:

- **Windows** — SmartScreen shows "Windows protected your PC". The reader has to
  choose *More info → Run anyway*. It gets quieter as more people install the
  same file, and stops entirely with an EV certificate.
- **macOS** — Gatekeeper refuses an unsigned `.dmg` outright. The reader has to
  right-click → Open, or clear the quarantine attribute. A Developer ID
  ($99/year) is the only real fix. The CI job builds macOS anyway, and is
  allowed to fail, so the pipeline is known to work before there is a
  certificate to use.
- **Linux** — nothing complains. AppImage needs the executable bit set.

Say so on the download page. A reader who meets SmartScreen with no warning
concludes the file is malware, which is the correct instinct.

## Size

The installer contains the whole bundle: the player, and every picture and sound
the release packaged. A novel with 100 MB of art produces an installer of roughly
that plus about 10 MB of shell. Nothing streams — the point of the channel is
that it works offline.

## Continuous integration

[`.github/workflows/desktop.yml`](../.github/workflows/desktop.yml) builds all
three platforms from a real release through the committed tools. It runs on
demand, and by itself when the desktop pipeline changes.

**The workflow has run, and all three platforms built** (run 33560229214):
Windows NSIS, Linux `.deb` (101.8 MB) and AppImage (173.6 MB), macOS `.dmg`
(105.7 MB, unsigned). The macOS runner is Apple Silicon, so that `.dmg` is
`aarch64` only — an Intel Mac needs an `x86_64` or universal build, which nothing
here produces yet.

The same pipeline also ran locally on Windows on 2026-09-01: `tauri icon`
generated the icons, `cargo` compiled the shell in about five minutes, and the
NSIS bundler produced a 107 MB installer whose name, identifier and version came
from the staged config. Launching the built binary opens a visible window titled
from that config, with a WebView2 child hosting the page.

The Windows build has been run and it plays — the author's own report, on
2026-09-02, not a measurement taken here. Where the evidence still stops: nobody
has run the Linux or macOS artifacts, and nobody has installed an update over an
earlier version.
A blank webview looks identical from outside. The
same frontend does play from `file://` with zero network requests under
`pnpm test:player-e2e`, and Tauri serves it from an easier origin than that — but
that is an argument, not an observation.
